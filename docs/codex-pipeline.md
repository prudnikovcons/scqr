# Codex × Claude pipeline

> Как устроен турникетный обмен графикой между Claude (редакция) и Codex (генератор картинок). У владельца всего две фразы.

---

## Две фразы владельца

**В Codex Desktop / Codex CLI:**

> Прочитай `D:\CODEX\gitscqr\scqr\.scqr\codex-inbox\START-HERE.md` и выполни всё, что там написано.

**Claude'у в чате (после отчёта Codex):**

> Codex закончил.

Между этими двумя фразами всё автоматическое: задания, генерация, подвязка обложек к статьям, обновление frontmatter и sidecar.

---

## Что происходит за фразой 1

1. Codex открывает `START-HERE.md` — один файл, в котором:
   - где брать задания,
   - формат задания,
   - стиль SCQR (палитра, маскот, ограничения),
   - что НЕ делать,
   - формат финального отчёта.
2. Codex перечисляет файлы в `.scqr/codex-inbox/`, фильтрует по `status: pending`.
3. Для каждого pending-задания читает тело-промт и генерирует PNG.
4. Сохраняет PNG по `target_path` из frontmatter (абсолютный путь).
5. Файл задания НЕ редактирует — это сделает watcher.
6. Если задание не получилось после двух попыток — ставит `status: failed` и `error: <причина>`, переходит дальше.
7. В конце выдаёт компактный отчёт `обработано N → M done`, `✓` и `✗` по каждому файлу.

## Что происходит за фразой 2

1. Claude сканирует `.scqr/codex-done/` — список новых файлов с момента предыдущей синхронизации.
2. Для каждого `type: cover` проверяет: PNG лежит по target_path, watcher уже подвязал `heroImage` к статье и `ogUrl` к sidecar. Если что-то пропустилось — поправляет руками.
3. Сканирует `.scqr/codex-failed/` — если есть, читает `error:` и предлагает либо переделать задание (с уточнениями), либо снять с пайплайна.
4. Докладывает владельцу:
   - что подвязано,
   - что в `failed`,
   - какие задания висят `pending` (если Codex не до всех дошёл),
   - что нужно от владельца дальше (нажать «Опубликовать» в `/queue`, посмотреть превью в `/editor` и т.д.).

---

## Кто что делает

| Слой | Делает | Не делает |
|---|---|---|
| **Claude** (редакция) | пишет статьи, формирует задания в `codex-inbox/`, забирает результаты, подвязывает их к статьям, докладывает | не генерирует растровых картинок |
| **Codex** (генератор) | читает `START-HERE.md`, делает PNG по описанию, кладёт по `target_path` | не редактирует ничего вне `codex-inbox/`, не трогает git, не правит статьи |
| **review-server watcher** | каждые 30 сек проверяет inbox, видит появление PNG, переносит задание в `done/`, для cover вызывает `importCodexCover` | не запускает Codex, если `SCQR_CODEX_CMD` пустой (тогда оставляет в pending — ждёт, пока owner запустит Codex руками) |
| **Owner** (Максим) | произносит две фразы | не копирует промты, не следит за путями, не правит frontmatter руками |

---

## Состояния задания

`pending` → `in_progress` (если включён авто-вызов Codex CLI через `SCQR_CODEX_CMD`) → `done` (PNG появился, перенесено в `codex-done/`)

или

`pending` → `failed` (Codex не справился, перенесено в `codex-failed/` с `error:`)

или

`pending` → остаётся в inbox (если Codex ещё не запускали; никто не блокирует)

---

## Расширения

- **Авто-вызов Codex CLI.** Если в `.env.local` указано `SCQR_CODEX_CMD="codex exec --full-auto"`, watcher не ждёт ручного запуска — сам вызывает CLI на каждое pending-задание. Owner ничего не делает между фразами вообще.
- **Не только обложки.** `type: mascot` / `illustration` / `infographic` обрабатываются так же, только без `importCodexCover` в финале — файл просто кладётся по target_path.
- **Failed-recovery.** Если задание упало, я могу составить новое с уточнениями (другой seed, упрощённая композиция, другой стиль) и положить в inbox с новым именем.
